# boiler-relay

Python control software for two heating systems on a BeagleBone. Hydronic is a boiler, pump and zone valves on GPIO, with an end switch on each valve. Electric is the Stairwell radiator behind a Zigbee relay over MQTT, with no end switch. The relay reports its own power state. Each zone has a `system` field, `hydronic` or `electric`. Each zone is one thread that runs a PID loop on a temperature from redis and drives its outputs. The boiler output follows the OR of the end-switch pins on the hydronic zone valves. An electric zone never calls the boiler.

## Branch state

`more_better_modular` is the development branch. It replaces the legacy flat scripts with the `boiler_relay` package. The legacy scripts are deleted, and `python -m boiler_relay` has not run end to end yet. The legacy scripts are still on `develop` and `main`, and in this branch's history up to `14882aa`. The device runs them today as `boiler_relay.service`.

Known breakage in the new code:

- `MQTTRelay` publishing has run against a real broker (paho-mqtt 2.2.0 on a Mac, topic `boiler_relay/test`), where the payloads arrived in order and a failed connection warned once and recovered. It has not switched the real Zigbee relay, and a broker dying mid-connection has not been tried. The report subscription, the confirmation, the silence retries and the refresh have only run against a fake client. On 2026-11-08 the relay answered every repeated command with a report, 17 of 17, at the 5 second cadence. Nobody has measured a repeat at the 60 second refresh interval, which the refresh and `confirmed_silent` assume.
- `deploy.sh`, `deploy/switch.sh`, the two unit templates and the legacy drop-in have not been run against a device. They have only run against stub `ssh` and `rsync`. The `Conflicts=` behavior, the drop-in after `daemon-reload` and `enable` on the copied units are unchecked.
- The device runs Python 3.7.3. A clean install of `requirements.txt` and the tests pass on `python:3.7.17` in Docker. Neither has run on the device itself.

## Layout

- `boiler_relay/__main__.py`: entry point, run as `python -m boiler_relay`. Reads `--config` (default `config/system_config.json`, resolved from the project root), builds the zones and the boiler, starts them, and exits non-zero if any thread stops. `--shadow` runs the same decisions with no outputs, see `state_publisher.py`. `SIGTERM` stops everything and drives the outputs inactive. Invalid config exits 2.
- `boiler_relay/zone.py`: `Zone` is a thread. Every 5 seconds it reads temperature, setpoint, target state and boost from redis, runs the PID, turns the control value into a duty cycle over a `control_interval` minute window, writes `control_value` and `heating_cooling_state` to redis, and calls `activate` on each output. The PID samples every `pid_interval`. `COOL` and unknown target states are off. With `mode="shadow"` a zone builds no outputs, skips the Homebridge keys and only publishes through the `StatePublisher`. A reading whose sample time has not changed for two hours calls for no heat. Three failed ticks in a row drive the outputs inactive, and the zone keeps retrying.
- `boiler_relay/pid.py`: `PID`, our own controller, because `simple-pid` has no separate integral limit. Proportional on error, derivative on measurement, integral clamped to 0 up to `integral_cap`, output clamped to 0 to 1. `reset()` clears the integral. With the default gains it equals `simple-pid` 2.0.1 sample for sample, which `tests/test_pid.py` checks, so `simple-pid` is in `requirements-dev.txt` only.
- `boiler_relay/boiler_thread.py`: `BoilerThread`, turns the boiler output on when any end-switch pin is high. The pins come from the `end_switch` key on each zone's gpio outputs. Three failed polls in a row drive the boiler inactive. Each poll publishes the call and a heartbeat. `ShadowBoilerThread` replaces it in shadow mode. It reads no pin and calls the boiler when any zone with an `end_switch` output has decided heat. The config allows an `end_switch` only on hydronic zones.
- The read-only API and web interface are not in this repo. They live in `heating-web`, which deploys and versions apart from this service. It reads the redis keys below and this project's `config/system_config.json`, using only each zone's `name`, `sensor_path` and `system`. Keep those three fields.
- `boiler_relay/state_publisher.py`: `StatePublisher` writes JSON under `heating/<mode>/`, where mode is `active` or `shadow`. Keys are `zones/<name>` (`system`, `control_value`, `state`, `pid`, `confirmed`, `confirmed_time`, `time`, where `pid` is the `kp`, `ki`, `kd` and `integral_cap` the zone runs, and `confirmed` is the relay's last reported power, 0 or 1, with `confirmed_time` its UTC time, both null for a hydronic zone, in shadow mode and before the first report, and `confirmed_silent` is true while a command has gone 5 seconds unconfirmed, false otherwise, null for a hydronic zone and in shadow mode), `hydronic/boiler` (`call`, `time`) and `heartbeat` (`time`). These keys use the zone name, not the sensor path. Shadow mode writes nothing outside `heating/shadow/`.
- `boiler_relay/version.py`: `__version__`, one semantic version for this service, with a `vX.Y.Z` git tag per release. `python -m boiler_relay --version` prints `boiler_relay <version> (<commit>)`. The commit comes from `build_info.json` at the project root, which `deploy.sh` writes and git ignores, and reads `unknown` when the file is missing. At startup `state_publisher.publish_version` sets `heating/versions/boiler-relay` to `{"version", "commit", "time"}` in both modes. A redis error there logs a warning and the service keeps running.
- `boiler_relay/outputs/`: one file per output type. `actuator.py` is the `Actuator` base class with `start`, `stop`, `activate(value)` and `status()`, which returns `None` unless the output confirms its state. `gpio_output.py` is `GPIOOutput` (`type: gpio`, one `pin`, optional `end_switch`). `mqtt_relay.py` is `MQTTRelay`, which keeps only the latest value and sends it from a worker thread so a slow broker never stalls the zone. It subscribes to `tele/<gateway>/+/SENSOR`, derived from the `cmnd/<gateway>/ZbSend` command topic, on the same client and again on every connect. It reads `Power` and `LinkQuality` from `ZbReceived` for its `Device` and ignores `stat/.../RESULT`, other devices and malformed payloads. It sends the first decision after start, a change, the tick after a failed publish (a publish error code counts as failed), a decision after a report that differs from the last command, and a resend after silence of 5 seconds, then 10, 20 and so on up to 120. It also sends the current state again once nothing has been sent for `refresh_interval` seconds, so a relay that rejoined in the wrong state is corrected. The refresh goes through the same send, so it waits for a report and backs off like any other. `confirmed_silent` comes from the time of the first unconfirmed command, which a resend does not reset, and a matching report clears it. Only `activate` decides to send, so the zone's 5 second tick paces every resend. A command topic not shaped `cmnd/<x>/<y>` sends on change and on the refresh, with no subscription and no silence retries. `Zone.confirmation` passes its output's `status()` to the publisher. `__init__.py` holds `create_output`. A new output type is a subclass with an `output_type` string, constructed as `(output_config, mqtt_config)`, imported in `__init__.py`. `create_output` raises `ValueError` for a missing or unsupported type, and an `MQTTRelay` raises without an `mqtt` section.
- `boiler_relay/config.py`: dataclass configs. `SystemConfig.from_file` parses the whole file and raises `ConfigError` for a missing section, an unknown key, a missing or unknown zone `system`, an `end_switch` on an electric zone, a config with no hydronic zone that has an `end_switch`, mixed output types in a zone, `active_low` on an output, duplicate zone names or sensor paths, or a GPIO pin used twice.
- `boiler_relay/gpio.py`: exports `GPIO`, a lazy `GPIOLoader`. The first call imports `Adafruit_BBIO.GPIO`, and a stub that logs replaces it when that import fails. `GPIO.use_stub()` picks the stub without importing anything. `__main__.py` calls it right after parsing `--shadow`, so shadow mode never imports `Adafruit_BBIO`. `gpio_output.py` and `boiler_thread.py` import `GPIO` from here.
- `boiler_relay/heating_cooling_state.py`: the `HeatingCoolingState` enum.
- `config/system_config.json`: the config, with `mqtt` (optional, with an optional `refresh_interval` in seconds, default 60, positive), `redis`, `zones` and `boiler`. Sensor paths are the friendly names the legacy system uses. A zone is one sensor, one PID and one kind of output, and it names its `system`. Stairwell is `electric` and every other zone is `hydronic`. The end switch pairings were checked on the device by boost tests on 2026-11-07. For Bedrooms, both switches rose with both outputs on, and the test cannot say which switch belongs to which output. Common (`P8_15`) and Kitchen (`P8_7`) were swapped in the old config. `BoilerThread` sets every end switch input to gpio mode with the pull disabled, because `P8_17` powers on with a pulldown and reads low until it is set. The BackRoom end switch (`P8_27`) is faulty and can stay high after the output turns off, which keeps the boiler on with no demand until it is replaced. Optional zone keys are `control_interval` (duty window in minutes, default 10), `active_low` and `pid` (`kp`, `ki`, `kd`, `integral_cap`, defaults 1, 0.01, 0.5 and 1.0, validated at load). An optional top-level `pid` block is the default for every zone with no `pid` of its own, hydronic and electric alike, so Stairwell follows it unless it has its own. The precedence is the zone's block, then the top-level block, then the built-in values. A zone block replaces the default as a whole, and `SystemConfig.from_dict` applies the top-level block. A bad top-level block raises `ConfigError` naming the top-level `pid`. The shipped config writes it out as 1, 0.01, 0.5 and 1.0. The Study zone has its own `pid` block with the shadow's candidate gains (1, 0.001, 0 and 0.3), so the active service runs it beside zones on the defaults for comparison. The optional `shadow` section holds a `pid` block that replaces the `pid` of every hydronic zone in shadow mode only, whatever the zone or the top-level `pid` says. The active service ignores it, and an electric zone in shadow mode follows the active precedence, through `SystemConfig.zones_for`. The shipped config sets it to Kp 1, Ki 0.001, Kd 0 and a cap of 0.3, so the shadow runs candidate gains while the legacy controller keeps its own.
- `deploy.sh`, `deploy/`: sync the project and a generated `build_info.json` to the device with `rsync --delete` and build a virtualenv. `*.template` files hold `<service_name>` and `<service_user>` placeholders. The service is `boiler_relay_v2`, installed in `/var/lib/boiler_relay_v2` with the virtualenv in `.venv`, which the sync keeps. It runs as `SERVICE_USER`, default `heating`, which the caller creates. `deploy.sh` refuses `/var/lib/boiler_relay` and `/home/debian/boiler-relay`, the legacy service's locations. `setup_python.sh` runs the venv build and every pip install under `nice -n 19 ionice -c3`, so they cannot starve the live service on the single core. The generated `setup_python.sh`, `boiler_relay_v2.service` and `boiler_relay_v2_shadow.service` are gitignored.
  - `boiler_relay_v2.service` conflicts with `boiler_relay.service` only. It orders after `redis-server` and `mosquitto`, because the Stairwell relay needs the broker.
  - Both service units use `Restart=on-failure`, `RestartSec=5` and `StartLimitIntervalSec=0` in `[Unit]`, so a boot that starts them before redis or mosquitto is ready cannot leave them stopped. A config that fails to load restarts them every 5 seconds without end.
  - `boiler_relay_v2_shadow.service` declares no `Conflicts=` and v2 does not list it, so the two can run together. `Conflicts=` works both ways, which is why v2 must not name the shadow. It orders after `redis-server` and `mosquitto`, and its `[Install]` section starts it at boot once enabled. Nothing enables it except `switch.sh shadow` or a manual `systemctl enable`. It runs `python -m boiler_relay --shadow`.
  - `deploy/boiler_relay.service.d/conflicts.conf` is the legacy unit's drop-in. It makes legacy conflict with v2. `deploy.sh` prints the command that installs the units and the drop-in on the device.
  - `deploy/switch.sh <user> <host> legacy|v2|shadow [--confirm]` runs over `ssh -t` with sudo. It stops the old services and waits until they are inactive. It starts the new ones and moves the boot-time enable only after they stay up. `shadow` starts and enables legacy and the shadow unit, because stopping v2 alone would leave the boiler uncontrolled. `legacy` stops the shadow and disables it at boot. `v2` stops and disables only the legacy service and leaves a running shadow alone, so the shadow can run candidate gains beside v2. `v2` lists the running units it will stop and exits without changing anything unless `--confirm` is given. It never touches `mqtt_bridge.service`.
- `docs/img/`: images for the README.

## Redis contract

The Homebridge plugin and the MQTT bridge share these keys. Do not rename them. Each zone has a `sensor_path` such as `/home/sensors/kitchen`.

- `<sensor_path>/current_temperature`: JSON `{"value", "time"}`. Written by the MQTT bridge.
- `<sensor_path>/target_temperature`: JSON `{"value"}`. Written by Homebridge.
- `<sensor_path>/target_heatingcooling_state`: int, `HeatingCoolingState`. 0 is off and 1 is heat. Anything else is treated as off.
- `<sensor_path>/control_value`: float 0 to 1, PID output. Written by the zone.
- `<sensor_path>/boost`: JSON boolean, forces the valve open.
- `<sensor_path>/heating_cooling_state`: set and published by the zone.

The zone and boiler threads also write state under `heating/<mode>/`, listed under `state_publisher.py` in Layout. Nothing else reads these keys except the `heating-web` service.

## Conventions

- Two-space indent in `__main__.py`, `config.py` and `outputs/`, four in `zone.py` and `boiler_thread.py`. Match the file you edit.
- One thread per zone, one per MQTT relay and one for the boiler. Loops run until `stopping` is set, with a `sleep(interval)` outside the `try`. Outputs are called, not polled.
- Log with `logging`. INFO is for state changes, window summaries and warnings. Per-tick detail is DEBUG. Warn once per condition, not once per tick.
- `active_low` is set per zone and applies to its gpio outputs. `GPIOOutput.activate` inverts at the last step before `GPIO.output`.
- GPIO pin names are BeagleBone headers such as `P8_10`.
- Tests live in `tests/` and use pytest with fakeredis and a recording GPIO. Run `.venv/bin/python -m pytest`. Loop threads are stopped by a fake `sleep` that raises, see `run_ticks` in `tests/conftest.py`.
- No linter. Run `python -m boiler_relay` to smoke test with the stub GPIO. It needs a local redis.
- Update `README.md` and `CLAUDE.md` before you commit a change, so the code and its docs land in one commit. A change to behavior, config or a published key needs both checked. Do not add a docs-only commit afterwards.
- When another session asked for the work, push each commit to `more_better_modular` once it is made, then message that session without asking the user. Say what was done, the commit hashes, the tip, and any tag or deploy that did not happen. Ask the user before you tag. Tell the session the work is ready to tag. Work the user started themselves still needs the user's approval for a push, a tag and a message to another session.
- CI runs `pytest` on Python 3.7 and 3.11 (`.github/workflows/test.yml`). It has not run yet.

## Setup

```
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
```

`Adafruit-BBIO` fails to install off the BeagleBone. `requirements-dev.txt` leaves it out and lists the other dependencies itself. `requirements.txt` pins `typing-extensions` because `paho-mqtt` 2.1.0 imports it on Python 3.7 without declaring it.
